## capella-fabric: Reading and Changing a Model Safely

### Reading a model

```
clone_capella_repo → add_dependency_repo (once per library) → list_object_types
    → browse_model / search_model_objects → resolve_model_uuids → generate_fabric
```

- **`list_object_types()` first.** It returns the valid phase and object-type combinations, so you aren't guessing names like "Physical Component" versus "PhysicalComponent".
- **`browse_model(session_id, phase, object_type)`** lists every element of a type in a layer. **`search_model_objects`** finds them by name.
- **`resolve_model_uuids`** takes the IDs you care about, and **`generate_fabric`** turns them into a structured YAML view of those elements and their relationships.
- **Add library repos before browsing.** Elements that live in a library don't appear until its repo is added.

Some elements are searched **across the whole model** rather than within one layer, because they don't belong to a single layer: data-modeling elements (classes, associations, exchange items, data types) and requirements. Pass any phase; you'll get all of them.

### Diagrams: read the `layer` field, not the `viewpoint`

Searching diagrams under a phase returns **that phase's diagrams**, worked out from the layer containing the element each diagram targets. So `[LFCD] Generate Power` appears under LA, where it was drawn.

**Do not read `viewpoint` as the layer.** It is the *Sirius* viewpoint, and it groups diagrams by **kind**, not by Arcadia layer. Every functional-chain description, sequence diagram, state machine and class diagram reports `Common` regardless of which layer it came from — on a real model that is 26 diagrams out of 88, drawn from the system, logical and physical layers together. Treating `Common` as a layer mixes all three into one bucket.

**Each diagram result carries a `layer` field** giving the real answer: `OA`, `SA`, `LA`, `PA` or `EPBS`. The Fabric Generator website shows the same value in its layer column.

**The one thing shown under every phase** is a diagram belonging to none — an EPBS diagram, or one whose target can't be resolved. Those appear under all four rather than none, so no diagram is ever unreachable. That matters because Capella's own per-layer diagram accessors filter on a single fixed viewpoint name each, which hid every `Common` diagram from every phase at once.

### Telling actors from components

**In Capella, an actor isn't a separate kind of element. It's a component flagged as an actor.** At the operational layer, it's an entity with the same flag. So an actor's `type` reads `PhysicalComponent`, `LogicalComponent` or `SystemComponent`, exactly like any other component. That's accurate, and it means `type` alone can't tell you which is which.

Look at **`is_actor`** instead. It's on every component and entity in browse and search results, and in `generate_fabric` output.

- **`object_type="Actor"`** lists only the actors in a layer.
- **`object_type="Component"`** still lists everything, actors included, each row saying which it is.

**Don't treat two similarly named components as duplicates without checking `is_actor` first.** A common and correct modeling pattern pairs an **actor** (the external entity itself) with a **behavior component** carrying its function, often with nearly the same name. Without looking at the flag, the pair reads as accidental duplication, and cleaning it up would delete deliberate modeling.

### Changing a model

```
clone_capella_repo → browse/search to confirm target IDs → apply_model_patch
    → verify_model → push_model_changes
```

**Follow these steps in order.** A change to the wrong element costs more to undo than to get right:

1. **Confirm the element's ID** by searching or browsing. Don't patch by name, and don't patch from an ID you remember.
2. **State the intended change** to the user in plain terms.
3. **Apply it** with `apply_model_patch`. Pass `author_name` and `author_email` so the resulting commit is attributed to the person who asked for it.
4. **Verify** by re-querying the element, and run `verify_model(session_id, phase)` on the layer.
5. **Log it** in `knowledge-repo`, with the commit it produced.
6. **Push only when the user confirms.**

**Run `verify_model` before large changes, not just after.** It checks a layer for elements with missing names and for functions not allocated to any component. Knowing what was already wrong keeps you from blaming your own change for an existing problem.

Patch syntax (targeting elements, setting attributes, adding children, forward references within one patch) is in **capella-fabric's own `instructions` field**. It's detailed, and kept current with the server. This handbook deliberately doesn't repeat it.

### Pushing, and trusting the answer

`push_model_changes` reports one of three outcomes, and **each one means something different**:

- **Pushed** — your changes are on the remote.
- **Already up to date** — nothing new was sent, because the remote already had these commits. Not a failure.
- **Rejected, with a reason** — a real problem, such as the remote having moved on or an authorization that has lapsed. Read the reason.

**Trust that response.** Re-cloning to double-check a push costs another authorization and tells you nothing the response didn't. If a push is rejected because the user's GitHub authorization expired, the message will say the changes are **still committed locally**; nothing is lost while the session is alive.

### Working on a model together

When two people take turns on one model (one edits in Capella Studio and pushes, the other works through an agent), **use `pull_model_changes` to pick up the other person's pushes.** It works in the session you already have, with no new clone and no new authorization. **Don't re-clone to see someone's edits.**

It reports one of three outcomes:

- **Up to date** — nothing new on the remote. It also mentions any of your own commits not yet pushed.
- **Pulled** — their commits are now in your session, each listed with author and message. **Re-browse before patching:** IDs you looked up earlier may no longer be right.
- **Diverged** — you both changed the model since you last synced. **Nothing was changed.** Both sets of commits are listed. **Tell the user before going further.** `pull_model_changes(discard_local_changes=True)` takes the remote version and names the local commits it dropped, so they can be reapplied on top.

If a push is rejected because the remote moved on, the rejection says the same thing: pull first.

A session left idle for about four hours is cleaned up; any tool use resets that clock.

### Keep the record separate

Everything above changes the model. **The reasons for a change — the observation that prompted it, the decision, what you learned — go to `knowledge-repo`**, not capella-fabric. A good habit: after pushing, log a decision that names the elements changed and the commit.
