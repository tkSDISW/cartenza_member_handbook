## Connecting to a Repo: PATs, Connect Codes, and Sessions

Before you can read or write anything, you have to get at a repo. There are several ways in, and one of them costs a human their attention — so it's worth understanding what you're spending.

**Every `begin_connect` interrupts a person.** They stop, open a browser, and authorize. One real session generated roughly a dozen of these in a single afternoon for what the user experienced as one continuous piece of work (`After_Treatment_System_Notebook`/`Fabric_MCP_Issues`, OBS-0003). Some of that was unavoidable. A good part was not, and this page exists so the avoidable part stops happening.

### Which path are you on?

| Situation | Use |
|---|---|
| **The repo is in your scope and its owner has connected it with GitHub** — try this first | The server's session tool with `remote_url=` and `agent_id=`, **no credential** |
| The repo is public (the Member Handbook, the routine-library) | The session tool with `remote_url=` alone — read-only |
| You can safely pass a PAT as a tool argument (e.g. Claude Code, PAT read from an environment variable, never authored by you) | `pat=` directly on the server's session tool (`github_pat=` on `clone_capella_repo`) |
| Nothing above applies — first connection, or a PAT-linked repo | That server's `begin_connect`, then its session tool with `connect_code=...` |

**Start with the first row, every time.** A repo whose owner has authorized it with "Connect via GitHub" can be opened again, and again, with no browser trip: the authorization they gave is stored and reused. It costs them nothing and you can call it as often as you need. Only when it comes back with an error do you go to `begin_connect` — and the error tells you which thing the human actually has to do (add a scope, or connect the repo with GitHub).

If you're on the second path: **don't try to disguise or reformat the credential to get it past your own safety layer.** That layer is right. `begin_connect` is the supported way through — it returns a plain, non-secret URL you can print verbatim (grounded in Cartenza's internal design history for the connect flow).

### Every server has its own connect, and its own session

Each of Cartenza's four servers connects independently. **A code is minted by one server and redeemed on that same server** — it won't work anywhere else.

| Server | Connect | Redeem with |
|---|---|---|
| `knowledge-repo` | `begin_connect(agent_id, remote_url, branch)` | `clone_knowledge_repo(connect_code=...)` |
| `workspace-manager` | `begin_connect(agent_id, remote_url, branch)` | `create_workspace_session(connect_code=...)` |
| `project-artifact-repo` | `begin_connect(agent_id, remote_url, branch)` | `create_session(connect_code=...)` |
| `capella-fabric` | `begin_connect(agent_id, repo_url, branch)` — note **`repo_url`** | `clone_capella_repo(connect_code=...)` |

### Three rules that save the human real interruptions

**1. A failed session start does NOT consume your connect code.** The code is spent only when the clone actually succeeds. So if the session tool fails — wrong branch, empty repo, no `.aird` file, repo not pushed yet — **fix the cause and retry with the same code.** Do not go back and ask for a new link. The error message tells you this explicitly; before it did, one user discovered it by trial and quite reasonably decided not to rely on it, buying extra browser trips they didn't owe.

**2. A connect code has two separate clocks — 4 hours to authorize, then 1 hour to redeem.** The first window runs from `begin_connect` until the human authorizes in the browser; during it the code holds nothing sensitive. The second runs from their authorization until you redeem it; during it the code holds the actual credential. Expiry in either window is the *only* condition, besides a successful redeem, under which the user genuinely needs a new link.

The two failures say different things, and the difference is worth acting on. *Expired before it was authorized* means the user never opened it — offer a new link. *Authorized more than an hour ago and lapsed* means they did the work and you were slow to follow up — worth apologizing for, and the stored credential has already been discarded. **Don't preemptively offer a fresh link because time has passed.** If the user says they authorized it, redeem.

**3. Prefer "Connect via GitHub" over pasting a PAT.** When the user reaches the connect page they get both options, and the difference outlives this one connection. The GitHub authorization covers *their other repos too*, so on `capella-fabric` a model's library repos need no further credential — `add_dependency_repo` just works. It also **stays available afterwards**: every later session on that repo resumes from it with no browser trip at all (the first row of the table above). A pasted PAT is a single-use snapshot, cleared when the code is consumed — so every dependency needs its own code, and so does every session after this one.

### Sessions are cheap; authorizations are not

A `session_id` is not a login. It's a handle to a server-side clone, and it can go away:

- **`knowledge-repo`, `workspace-manager` and `project-artifact-repo`** sessions live in memory and vanish when that server restarts, with no warning.
- **`capella-fabric`** sessions are swept from disk roughly 4 hours after last use.

Either way you get "Unknown session_id" on the next call. **Resuming is usually free:** call the session tool again with `remote_url=` and `agent_id=`, and for a GitHub-connected repo in your scope it picks up the authorization the user already gave. A public repo is free to re-clone too, and so is the direct-PAT path. It's only a **PAT-linked repo, or one never connected with GitHub, that costs a fresh human authorization.**

Free is not the same as free of friction, so still keep a session rather than churning through them:

- **Reuse the `session_id` you're holding.** Resuming costs a round trip and re-reads the repo; using the handle you already have costs nothing at all.
- **Don't call `cleanup_session` unless the user says they're finished.** A live session costs nothing to leave open. Ending one you'll want again is pure loss, and on a repo that isn't GitHub-connected it's a browser trip you just spent on their behalf.
- **Work in progress lives in the session.** Anything written but not yet pushed goes with it.

**Sessions are per server.** A single piece of work often touches several: log an observation in the notebook (`knowledge-repo`), record a routine's outputs (`workspace-manager`), promote a finished result (`project-artifact-repo`), change the model (`capella-fabric`). Each is independent, with its own session and its own connect. When those repos aren't GitHub-connected, that's four separate authorizations for one task — the multiplication that produced the dozen-authorizations afternoon.

So before starting, work out which servers the task genuinely needs, open each once, and keep each session alive for the whole task.

### If something goes wrong

`begin_connect` refuses anything outside the agent's registered scope — that check is what makes the returned URL safe to print. If it says the agent has no scope for a repo, the fix is on the human's side at `/onboarding/repos`, not something you can work around. `list_my_scopes` shows exactly what the agent can reach, and returns a link to a page the human can open to see the same thing. Likewise "No registered agent with id ..." means the `agent_id` you were given isn't registered *in that environment* (dev and production have separate registries).

## Historical Note — why the TTL changed

*Background only. Rule 2 above is the current rule; nothing in this section is operational guidance.*

This page originally said a code expired 15 minutes after `begin_connect`. That was true when it was written and was replaced on 2026-09-10 by the two-window model above.

**The two windows, for reference:**

| Window | How long | What the code holds during it |
|---|---|---|
| `begin_connect` → the human authorizes in the browser | **4 hours** | nothing sensitive — just a scoped request whose repo and branch were already checked against the agent's registered scope |
| authorized → you redeem the code | **1 hour** | the actual credential (an encrypted PAT, or a live OAuth connection id) |

**Why it changed.** Fifteen minutes was measured against how long the *agent* waits, not how long a *person* takes. Real round trips run from fifteen minutes to a couple of hours — someone hands over a link, goes into a meeting, comes back. The old TTL meant the human did the work of authorizing and *then* got told the code had expired, which is the most expensive possible way to lose a round trip.

**Rule 1 was unchanged by this and remains the important one:** a *failed session start* consumes nothing. Retry with the same code before ever asking for a new link. Expiry and failure are different situations, and nothing about lapsing marks a code as used — consumption still happens only on success.

**Reference:** Cartenza's internal design history for the connect flow (the change and its reasoning).
