## Before You Create a New Package

A package is a folder of related entries — the repo's own filing system. Creating one is cheap, which is exactly why it's worth a moment's thought first: **a package created in the wrong place is hard to undo.** There is no merge, and no delete you'd want to use casually, so a near-duplicate tends to stay, quietly splitting one subject across two homes.

This has already happened in real use. An agent logging a new idea created a package for it, not realising a package for exactly that purpose already existed — **differing only in capitalisation.** Two folders, same subject, split by a capital letter. It was caught in the moment and the entry re-logged in the right place, but the duplicate remains.

### Four things to do first

**1. Look at what's already there.** `list_artifact_packages` costs nothing. Read the names properly rather than scanning for an exact match — **package names are case-sensitive**, so `field_notes` and `Field_Notes` are two different packages that look identical when spoken aloud. Watch for singular and plural, underscores versus hyphens, and abbreviations of the same phrase.

**2. Read what the repo is for.** `get_repo_config(config_type="purpose")` and `"behavior_config"`. A repo's purpose says what belongs in it; its behavior_config says how the owner wants entries written. A new package has to sit inside both.

**3. Ask whether it genuinely fits** — not just "does this name already exist", but:
- Does an existing package already cover this subject, under a name you wouldn't have chosen?
- Does this subject belong in this repo at all, given its stated purpose?
- Would a reader looking for this later expect to find it here, or somewhere that already exists?

**4. If anything looks off, say so.** A likely duplicate, a mismatch with the repo's purpose, a name you're unsure about — **raise it with the person rather than deciding quietly in either direction.** Silently creating it and silently refusing to create it are both worse than asking. They know things about their own filing that the repo doesn't record.

### Naming, once you're sure it's new

Match the conventions already in the repo rather than importing your own. If existing packages are lowercase with underscores, use that. **Consistency in a repo matters more than any particular style**, because it's what stops the next near-duplicate from looking reasonable.

### When it's genuinely a new subject

Then create it — this isn't a discouragement. Packages exist to keep a repo navigable, and forcing unrelated work into one because it already exists is its own kind of mess. The discipline is a check before the act, not a reason to avoid it.
